## Журнал второго Mac, прислан владельцем

В `Untitled-1.txt` от владельца: запуск 2026-10-02 08:46:23, Accessibility granted,
tap создан, clipboard always allow, выбран Double Option. Затем:

- Записи предыдущего дня содержат `replaced` и повторные изменения clipboard. Их нельзя смешивать
  с текущей серией отказов по защите или считать доказательством версии/источника защиты.

Вывод: в показанных утренних попытках замена отменялась защитными проверками; системный secure input
точно был включён как минимум в двух терминальных попытках. Источник/владелец secure input пока
не установлен, текущее состояние после этих записей неизвестно. Отказ второго Mac не следует
объяснять найденной локальной гонкой двойного копирования.

Следующий шаг — прочитать PID владельца secure input на втором Mac во время сбоя и определить
соответствующий процесс. Автоматически отключать системную защиту или убирать проверку из ReTyper
не предполагается. [Документация Apple](https://developer.apple.com/library/archive/technotes/tn2150/_index.html).

### Владелец secure input установлен

Следующий скриншот владельца: в 09:21 снова `secure input`; диагностическая команда вернула
`78765 /Applications/OpenChamber.app/Contents/MacOS/OpenChamber`.
Это устанавливает процесс, удерживающий защиту на втором Mac, но не причину её включения.
В архиве установленного на текущем Mac OpenChamber не найдено буквальных вызовов
`setSecureKeyboardEntryEnabled`/`SecureEventInput`; отсутствие строки не исключает включения
защиты через системное поле или внутри runtime. Версии двух экземпляров не сверены.

Следующая проверка владельца: полностью завершить OpenChamber на втором Mac, проверить замену
в обычном текстовом редакторе, затем проверить поведение после повторного запуска OpenChamber.
До результата не считать проблему устранённой и не утверждать конкретный механизм утечки режима.

Владелец завершил OpenChamber: PID больше не выводится из IORegistry, но замена продолжает
отказываться. На следующем скриншоте независимый `swift -e` дважды вернул
`IsSecureEventInputEnabled() == true`; свежий отказ присутствует до 09:31:18.
Следовательно, состояние защиты реально сообщает сама система, а не только ReTyper.
Отсутствие PID в IORegistry не доказывает выключение защиты; текущий владелец/причина неизвестны.
Следующая проверка: пункт «Терминал → Безопасный ввод с клавиатуры»; если он выключен,
чистый вход после перезагрузки без запуска OpenChamber и проверка обычного редактора.

### История изменения защитной проверки

Владелец не может перезагружать рабочий компьютер и указал, что до обновления ReTyper работал.
`git log -p -- Sources/ReTyper/SystemReplacementHost.swift` установил конкретное ужесточение:

- 0.10.0: `isSecureField()` возвращал только `FocusedText.isSecure()` — AX-защиту фокусного поля.
- Коммит `5929d83` (выпущен как 0.10.1): добавлено
  `onMain { IsSecureEventInputEnabled() } || FocusedText.isSecure()`; 0.11.0 это унаследовала.
- Это причина, по которой любой true глобального флага теперь отменяет замену даже в обычном
  поле другого процесса. Сравнение только 0.10.1→0.11.0 было недостаточно для ответа владельцу.
- Production-код ReTyper не вызывает `EnableSecureEventInput`; его вызовы есть только в отдельных
  тестовых драйверах с парным отключением. Нет доказательств, что само обновление включило
  системный режим на другом Mac; версия последней работавшей там сборки пока не подтверждена.

Возможный пересмотр: вернуть проверку защищённости конкретного получателя для обычных редакторов,
сохранив запрет для настоящих защищённых полей и глобальный запрет записи клавиш в терминалах.
Это меняет действующий защитный контракт; до согласования владельцем production-проверка не меняется.
Проверка такого кандидата не требует перезагрузки компьютера.

## Согласованный возврат точечной проверки — 2026-10-02

Владелец явно одобрил предложение («да, хуячим»). Конституция обновлена до 11.0.0:
в обычных редакторах `SystemReplacementHost.isSecureField()` снова проверяет только
`FocusedText.isSecure()`. Все проверки глобального Secure Input в `TerminalRecorder`
и терминальной ветке `AppDelegate` сохранены. Системный режим не отключается приложением.

Новый нативный сценарий `--secure-input` включает защиту в процессе драйвера и вызывает
настоящий хоткей в обычном поле отдельного приложения. Исходные параметры восстанавливаются,
собственный Secure Input выключается после прогона. Результаты:

| Проверка | До | После |
|---|---|---|
| Обычное поле + глобальный Secure Input | FAIL: только раскладка, `secure field` | PASS: `ghbdtn` → `привет`, clipboard восстановлен |
| Двойное Copy + глобальный Secure Input одновременно | — | PASS: текст исправлен, clipboard восстановлен |
| Настоящий `NSSecureTextField`, известная тестовая строка | — | PASS: строка и clipboard не изменились, `secure field` |
| Terminal + глобальный Secure Input | — | PASS: строка не изменена, `secure input` |
| VS Code metadata-путь + глобальный Secure Input | — | PASS: последнее слово исправлено, файл сохранён и сверен |
| Обычный нативный набор после обоих исправлений | — | 11/11 PASS |

Артефакты: `$TMPDIR/opencode/retyper-005-{global-secure-red,global-secure-green,combined-green,secure-field,terminal-secure,editor-global-secure,field-final-native}`.
В `EditorRecoveryGuards` сценарий глобального режима теперь проверяет исправление обычного поля
(либо подавление самого хоткея системой), вместо прежнего ожидания blanket-отказа.

После последнего изменения production-кода: **120/120 unit-тестов** (09:45:29),
release-сборки arm64 и x86_64 с `MACOSX_DEPLOYMENT_TARGET=12.0` прошли.
Локальный кандидат запущен из проекта; установленный `/Applications/ReTyper.app` не перезаписан.
На момент этих прогонов тестовые окна были закрыты, проверки в реальном OpenChamber и на втором
Mac ещё не были подтверждены. Более позднее подтверждение OpenChamber приведено в текущем статусе.

### Минимальная версия macOS

Владелец спросил, поможет ли минимум macOS 26. Нынешние дефекты воспроизведены на современной
системе и обусловлены алгоритмом, а не старым deployment target. Минимум оставлен 12.0.
Современный [NSPasteboard.accessBehavior](https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-9k4t4)
уже учитывается диагностикой; `alwaysAllow` доступен с 15.4, а журналы обоих Mac показывали
`always allow`. Само повышение минимума не устранит гонку Copy или широкую защитную проверку.
