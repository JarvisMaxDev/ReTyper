# Модель данных и состояний замены

**Актуализировано**: 2026-09-09 | **Основание**: [spec.md](./spec.md), текущие `ReplacementModels.swift`, `AccessibilityTextClient.swift`, `KeyboardMonitor.swift`, `SyntheticInputGate.swift`, `AppDelegate.swift`, `TextReplacementCoordinator.swift`, `StatusBarFeedbackState.swift`, `CharacterMap.swift`, `TextConverter.swift` и `LayoutManager.swift` в `Sources/ReTyper/`

Описаны существующие типы, не предлагаемые интерфейсы. Постоянного хранилища у операции нет. Снимки живут во время выполнения; исходный фрагмент при `needsRecovery` переживает операцию **в памяти координатора** до явной очистки или завершения процесса. Прежние `ReplacementRequest`, `ClipboardBackup`, классы `readOnlyText` и цепочка `deleting -> pasting` больше не описывают реализацию.

## Данные

| Тип | Реальные поля / значения | Смысл и проверка |
|-----|-------------------------|-----------------|
| `TextAccessCapability` | `applicationPID: pid_t`, `activationPID: pid_t`, `element: AXUIElement`, `window: AXUIElement`, `let windowSource: TextWindowSource`, `elementRole: String`, `canSetValue: Bool`, `canSetSelection: Bool` | Получатель события, отдельный свидетель активации, ссылки на исходное поле/окно и неизменяемый источник окна. Вычисляемый `supportsReplacement` требует роль `AXTextField`/`AXTextArea`/`AXComboBox` и оба writable-признака |
| `TextWindowSource` | `.field`, `.application` | Прямой `AXWindow` поля либо резервный `AXFocusedWindow` того же активного приложения; выбирается при захвате и не перевыбирается при повторных проверках |
| `TextSnapshot` | `value: String`, `caretLocation: Int`, `selectionLength: Int`, `selectedText: String?` | Текст и диапазон в UTF-16. При непустом выделении `caretLocation` означает начало диапазона, не обязательно его активный конец и не курсор оболочки |

| `ReplacementOptions` | `applicationPID: pid_t`, `activationPID: pid_t`, `inputGeneration: UInt64`, `triggeredAt: TimeInterval`, `onlyLastWord: Bool`, `availableLayoutIDs: [String]` | Получатель, поколение и время передаются из решения хоткея без повторного захвата; делегат отдельно добавляет свидетель активации и настройки до фоновой работы. `triggeredAt` использует `systemUptime`, не календарное время |
| `PreparedTextInput` | `id: Int64` | Непрозрачный идентификатор подготовленного ввода; не текст и не подтверждение принимающего приложения |
| `InputDelivery` | `queued`, `cancelled`, `handedOff` | Локальный статус шлюза. `handedOff` не является ACK приложения |
| `ReplacementResult` | `outcome: ReplacementOutcome`, `targetLayoutID: String? = nil` | Результат координатора или раннего отказа; чистый `layoutSwitchAction` выбирает действие, а `AppDelegate.applyLayoutSwitch` выполняет его |
| `LayoutSwitchAction: Equatable` | `next`, `select(String)` | Намерение переключения без системного эффекта; отсутствие действия выражено `nil`, не отдельным случаем enum |
| `TextAccessError` | `unavailable`, `focusChanged`, `inconsistentSnapshot`, `invalidValue`, `timeout`, `system(Int32)` | Причины отказа внешнего источника, не разрешение запасного способа ввода |
| `AbortReason` | `noTextAccess`, `unsupportedField`, `invalidSnapshot`, `contextChanged`, `selectionNotEstablished`, `inputUnavailable`, `inputCancelled`, `recoveryPending`, `busy` | Метаданные отмены без пользовательского текста |

`AccessibilityTextClient` при захвате проверяет `acceptsEnabled(_:role:)`: присутствующий `AXEnabled` допускается только как фактический `CFBoolean true`, отсутствие только для `AXTextArea`; оба writable-признака остаются обязательными для замены. `false` и неверные типы отклоняются. `acceptsSubrole(_ value: CFTypeRef?) -> Bool` получает исходное необязательное значение: `nil` допускается, присутствующая нестрока и строка `kAXSecureTextFieldSubrole` отклоняются до построения capability. Эти признаки не хранятся отдельными полями модели. `optionalAttribute` возвращает `nil` для `.noValue`/`.attributeUnsupported`, остальные ошибки не превращает в отсутствие. Наличие writable-атрибутов является условием допуска, а не доказательством семантики клавиатурной замены.

## Идентификаторы раскладок

- `CharacterMap.cyrillicLayout(for:)` возвращает только `CyrillicLayout(rawValue: layoutID)`: `com.apple.keylayout.Russian` -> `.russian`, `com.apple.keylayout.RussianWin` -> `.russianPC`, `com.apple.keylayout.Ukrainian` -> `.ukrainian`, `com.apple.keylayout.Ukrainian-PC` -> `.ukrainianPC`, `com.apple.keylayout.Belarusian` -> `.belarusian`. Частичные и неизвестные ID не выбирают таблицу; существующие таблицы не расширены.
- `isLatinLayout(_:)` сравнивает полный ID с `com.apple.keylayout.<имя>` из закрытого списка: `ABC`, `US`, `British`, `USInternational`, `Australian`, `Canadian`, `USExtended`, `Colemak`, `Dvorak`, `Polish`, `PolishPro`, `German`, `French`, `Spanish`, `Italian`, `Portuguese`, `Dutch`, `Swedish`, `Norwegian`, `Danish`, `Finnish`, `Czech`, `Slovak`, `Hungarian`, `Romanian`, `Croatian`, `Slovenian`, `Turkish`. Это группировка для ручного переключения, не допуск конвертации; существующий `isEnglishLayout(_:)` делегирует ей. Подпись `displayName(for:)` также не определяет совместимость.
- `isSupportedLatinTarget(_:)` принимает только полные `com.apple.keylayout.US`, `com.apple.keylayout.ABC`, `com.apple.keylayout.PolishPro`. При кириллическом тексте `autoConvert` использует первую известную кириллическую таблицу и первую совместимую латинскую цель в порядке `availableLayoutIDs`; при отсутствии пары возвращает `(text, nil)`. При латинском тексте сохраняется выбор первой известной кириллической цели. Координатор без цели или изменения UTF-16 возвращает `layoutOnly` до выделения/подготовки, без создания recovery-копии.
- `LayoutManager.relevantLayoutIDs()` сохраняет приоритет установленных ID из `SettingsManager.activeKeyboards`, не фильтрует сохранённый ручной выбор до трёх автоматических целей и не перезаписывает настройки. Автоопределение применяется, если сохранённый список пуст или в нём нет доступных ID.
- После заполнения `belarusianToEnglish` из прямого словаря явно установлено `map["'"] = "]"`. Обе прямые пары `]`/`}` -> `'` остаются; канонический обратный выбор не зависит от обхода словаря и не восстанавливает потерянное состояние Shift. Это согласованное решение T046, не новая таблица.

## Привязка к хоткею

- `applicationPID` получается из `eventTargetUnixProcessID` завершающего события модификатора (`flagsChanged`), сопоставленного между session- и annotated-стадиями и распознанного как хоткей в `.cgAnnotatedSessionEventTap`. `KeyboardMonitor.checkedPID(_:)` принимает только положительное значение, точно представимое как `pid_t`, без усечения. При отсутствии корректного получателя `AppDelegate` отказывает с `noTextAccess`, а при уже сохранённом исходнике с `recoveryPending`; подстановки PID из `NSWorkspace` и запуска координатора в ранней ветке нет.
- `activationPID` независимо захватывается в обработчике хоткея из `NSWorkspace.shared.frontmostApplication`. Это свидетель состояния активации, а не получатель клавиатуры. Он может отличаться от `applicationPID`, если ввод получает неактивирующая панель поверх другого активного приложения.
- `inputGeneration` и `triggeredAt` приходят из `KeyboardEventStages.Decision.hotkey(pid_t?, UInt64, TimeInterval)`: сопоставленное `observed.generation` и переданное в обработчик стадии `now` по `systemUptime`. `KeyboardMonitor.onHotkeyTriggered` передаёт все три значения в `AppDelegate.handleHotkey(applicationPID:generation:triggeredAt:)`, а тот напрямую в `ReplacementOptions`, без нового чтения поколения или часов. Изменение активности после решения не становится новым исходным поколением операции.
- Перед захватом координатор требует положительные оба PID, конечное время, `0 <= startedAt - triggeredAt < 0.3` и неизменное поколение. Будущая метка, возраст **300 мс и более** или смена поколения дают `contextChanged` до обращения к AX. Абсолютный начальный дедлайн равен **`captureDeadline = triggeredAt + 0.3`**: время после решения, включая ожидание фоновой задачи, захват capability и исходный снимок, расходует один бюджет. После dispatch новые 300 мс не выдаются; срок проверяется также между capability и снимком и после снимка. Это не общий дедлайн всей операции: последующие этапы имеют собственные бюджеты подтверждения.
- Возвращённый `TextAccessCapability` должен сохранить **оба** PID из options. `AccessibilityTextClient` читает AX-дерево именно `applicationPID`, повторно сверяет тот же элемент и окно через сохранённый `windowSource`, а текущее состояние активации проверяет относительно `activationPID` до и после чтений фокуса.
- `resolveWindow` при захвате предпочитает `.field`: присутствующий `AXWindow` должен быть AX-элементом; неверный тип и реальные ошибки не разрешают резервный путь. Только отсутствие допускает `.application`: положительный `applicationPID == activationPID == текущий активный PID`, фактический `CFBoolean true` в `AXFocused` поля, AX-элемент из `AXFocusedWindow` приложения с ролью `AXWindow` и владельцы **поля и окна**, равные `applicationPID`. Дополнительные проверки роли окна и владельцев применяются только к `.application`; прямой путь сохранён. Повторная проверка читает только выбранный источник: потеря, неверное значение или ошибка не разрешают переключение `.field`/`.application`, даже если другой путь доступен.
- `acceptsActivation(_ currentPID: pid_t?, fieldFocused: Bool?)` требует положительные оба PID и `currentPID == activationPID`. При `applicationPID != activationPID` дополнительно обязательно `fieldFocused == true`: клиент читает `AXFocused` у уже сопоставленного поля и принимает только фактический `CFBoolean true`, не число/строку. Отсутствие атрибута, неверный тип или `false` не подтверждают фокус панели. При равных PID этот helper не требует атрибута, но для источника `.application` строгий фокус отдельно обязателен в `resolveWindow` при захвате и повторных проверках.

Свидетель активации проверяется заново клиентом и шлюзом, включая подготовку и передачу. Он не является независимым запросом фактического текущего получателя клавиатуры; единственный захваченный получатель относится к завершающему событию хоткея. Ни совпадение PID, ни положительный `AXFocused` не являются ACK приложения.

## Стадии перехвата

Один `KeyboardMonitor` владеет **двумя активными** перехватчиками (`.defaultTap`): `sessionTap` в `.cgSessionEventTap` и `annotatedTap` в `.cgAnnotatedSessionEventTap`, каждый со своим источником основного run loop. `isRunning` требует оба включённых перехватчика; `KeyboardEventStages` также получает их живую готовность. Отсутствие любого сбрасывает допуск шлюза и состояние хоткея, не разрешая новый ввод; завершение уже переданного key-down парным key-up остаётся допустимым.

`KeyboardEventStages` содержит `Stage` (`session`, `annotated`), `Decision` (`passThrough`, `drop`, `route(CGEvent, pid_t)`, `hotkey(pid_t?, UInt64, TimeInterval)`), детектор модификатора и единственное необязательное `modifierEvent: (timestamp: CGEventTimestamp, keyCode: Int64, sourceUserData: Int64, generation: UInt64)?`. Это один отпечаток события модификатора и его поколение, не очередь событий. `CGEventTimestamp` нужен для сопоставления стадий; `triggeredAt` отдельно фиксирует монотонное время решения хоткея, не копирует timestamp события.

- Session-стадия обрабатывает собственные транспортные токены через шлюз, а чужую пользовательскую активность учитывает сразу через `gate.recordActivity() -> UInt64`. Увеличение и возврат поколения выполняются под одной блокировкой. Для `flagsChanged` сохраняются отпечаток `(timestamp, keyCode, sourceUserData)` и **именно возвращённое** поколение; обычные клавиши, мышь и другая учитываемая активность сбрасывают сопоставление.
- Annotated-перехватчик подписан **только на `flagsChanged`**. Хоткей допускается при точном совпадении отпечатка и `observed.generation == gate.activityGeneration`, причём поколение должно быть меньше `UInt64.max`. Отпечаток потребляется однократно; несовпадение, вмешательство или нарушение порядка сбрасывает готовность хоткея. Эта стадия не увеличивает поколение повторно; решение сохраняет именно `observed.generation` вместе с получателем завершающего события и `now`, а не перечитывает поколение для передачи делегату.
- Annotated-стадия не применяет транспортный фильтр к process-targeted Unicode-эху `postToPid`. Собственные события здесь проходят без изменения, не становясь пользовательской активностью. Защита от повторного встраивания собственных событий в session-поток остаётся на session-стадии.

Для сопоставления стадий не сохраняются `CGEvent`, Unicode-содержимое или история обычных клавиш. Подготовленный текст конкретной операции существует отдельно в `SyntheticTextPayload`, а не в отпечатке хоткея.

## Строгий снимок

1. Начало и длина неотрицательны; начало не превышает длину значения; длина сравнивается с оставшейся длиной **до сложения**, чтобы не допустить переполнение.
2. Обе границы совпадают с границами расширенных графем. Некорректный диапазон отклоняется без clamping, snapping и нормализации.
3. Если `selectedText` доступен, его UTF-16 должен точно совпасть с подстрокой указанного диапазона. Канонической эквивалентности недостаточно; отсутствие атрибута допускает извлечение из проверенного `value`.
4. `matches(value:range:)` проверяет полное значение по UTF-16 и точные числа диапазона. Для успеха диапазон пуст и находится после вставленного фрагмента.
5. Клиент сравнивает два последовательных валидных чтения и проверяет фокус вокруг них. Это защита от наблюдаемой несогласованности, не атомарный снимок чужого приложения.

## Подготовленный ввод

`SyntheticTextPayload` содержит `down` и `up`. Подготовка разрешает один непустой фрагмент до **4096 единиц UTF-16**, проверяет точное локальное чтение обоих событий обратно и может отклонить более короткий текст при ограничении платформы. Нет дробления на несколько вставок или отдельного удаления.

Внутренний `SyntheticInputGate.Ticket` связывает `targetPID` (исходный `applicationPID`), отдельный `activationPID`, поколение, монотонный дедлайн, подготовленную пару и инертные `.null`-сигналы. Ёмкость ограничена 32 билетами. `prepare` сверяет живой свидетель активации до и после создания пары; `takeSignals`, обработка down-сигнала и `delivery` повторяют проверку свидетеля, поколения, дедлайна и доступности шлюза. Запоздавшее уведомление об активации не заменяет эти чтения.

`KeyboardMonitor` глобально отправляет только `.null` **в `.cgSessionEventTap`**, где активный session-шлюз обрабатывает сигналы и разрешает `postToPid` сохранённому `targetPID`. Переход `.null` до annotated-стадии не требуется. Его `eventTargetUnixProcessID` (`null.targetPID` в диагностике) является метаданными, **не свидетельством получателя клавиатуры**; шлюз не использует его для допуска или выбора адресата. Собственные токены не становятся пользовательской активностью и не используются повторно.

Историческое основание разделения стадий: [контролируемая проба key-up в собственный PID](./research.md#основания-и-границы-свидетельств) выявила annotated-эхо и его ошибочную фильтрацию промежуточным единственным annotated-шлюзом. В текущей схеме транспортная фильтрация ограничена session-стадией, а annotated-перехватчик `flagsChanged` не отбрасывает Unicode-пару на пути к получателю. Текущие результаты проверок: [verification.md](./verification.md#текущий-статус).

```text
queued -> cancelled
queued -> handedOff
handedOff -> handedOff при cancel
```

`cancelled` доказывает отсутствие передачи подготовленного key-down через этот шлюз. После `handedOff` отмена не доказывает недоставку. Парный key-up обслуживается даже после смены контекста, без повторного текстового ввода. `finish` завершает срок жизни квитанции; неизвестная/уже освобождённая квитанция не трактуется как доказанная отмена.

## Итог операции

| `ReplacementOutcome` | Условие | Последствия |
|----------------------|---------|-------------|
| `replaced` | Наблюдается полное ожидаемое значение, правильный курсор, пустое выделение, проверенный контекст | Подтверждённый успех, возможна смена на целевую раскладку |
| `layoutOnly` | Нет фрагмента или полезной конвертации | Ввод не отправляется; возможна смена на следующую раскладку |
| `aborted(AbortReason)` | Нет допуска, контекст изменился до передачи, отменено queued-событие либо операция заблокирована | Новый текст не отправляется этой попыткой; `busy` не даёт нового сигнала, `recoveryPending` сохраняет предупреждение |
| `restoredAfterFailure` | Полный преобразованный текст с неверным курсором адресно заменён исходным и результат подтверждён | Одна попытка восстановления, сигнал неуспеха, без переключения раскладки |
| `needsRecovery` | После передачи не подтверждён итог либо единственное допустимое восстановление | Исходный фрагмент в памяти, постоянное предупреждение и блокировка новых замен |

### Политика переключения

`ReplacementResult.layoutSwitchAction(activationPID:currentActivationPID:inputGeneration:currentInputGeneration:) -> LayoutSwitchAction?` является чистой функцией. Первые два аргумента имеют тип `pid_t?`, последние два `UInt64`; требуются положительный исходный свидетель, его точное совпадение с текущим и равенство поколений. Получатель, часы, настройки и системные вызовы в функцию не входят.

При выполненных условиях `replaced` с целью даёт `.select(targetLayoutID)`, без цели `nil`; `layoutOnly` и обычный `aborted` дают `.next`. Для `busy`, `contextChanged`, `recoveryPending`, `needsRecovery` и `restoredAfterFailure` результат всегда `nil`, даже при наличии цели. `AppDelegate.applyLayoutSwitch` применяет эту политику и после координатора, и при раннем отсутствии получателя/свидетеля; имеющийся recovery в ранней ветке превращает отказ в `.aborted(.recoveryPending)`. Повторные чтения текущей активации/поколения служат только сравнению, не замене свидетельств хоткея. `LayoutSwitchPolicyTests` проверяет решение, не весь делегат или фактическую смену системной раскладки; результаты: [verification.md](./verification.md#текущий-статус).

## Состояние обратной связи

`StatusBarFeedbackState` отделяет краткий визуальный сигнал от сохраняемого объяснения исхода. Пользовательский текст в этом состоянии не хранится.

| Поле / свойство | Реальный тип / значение | Назначение |
|-----------------|------------------------|------------|
| `failureFlashDuration` | `static let`, `1.5` | Длительность краткого сигнала в секундах, не срок жизни объяснения |
| `isRecoveryAvailable` | `Bool`, изначально `false`, с `didSet` | Доступность ручного восстановления; переход `true -> false` очищает `lastFailure`, но не дедлайн сигнала |
| `failureFlashDeadline` | `private Double?` | Монотонный срок окончания краткого сигнала |
| `lastFailure` | `private ReplacementOutcome?` | Последний записанный неуспешный исход, не сохранённый исходный фрагмент |
| `outcomeMessage` | Вычисляемое `String?` | Фиксированное объяснение по `isRecoveryAvailable` и `lastFailure`, не отдельное хранилище сообщения |

- `recordOutcome(_:)` для неуспешного исхода заменяет `lastFailure`, но само не запускает краткий сигнал. `flashFailure(at:)` отдельно задаёт дедлайн `uptime + 1.5` и не меняет объяснение.
- `recordOutcome(.replaced)` и `recordOutcome(.layoutOnly)` очищают `lastFailure` и `failureFlashDeadline`. При отсутствии восстановления исчезают и сообщение, и краткий сигнал; сам `isRecoveryAvailable` этим методом не меняется.
- `recordOutcome(.aborted(.busy))` не меняет ни причину, ни дедлайн. Повторное присваивание `isRecoveryAvailable = false` также не стирает обычный отказ: `didSet` очищает причину только при переходе из `true`.
- `showsWarning(at:)` возвращает `true`, пока доступно восстановление или не истёк дедлайн. Истечение 1,5 секунды, чтения состояния, смена раскладки и старые таймеры не очищают `lastFailure`: объяснение остаётся в панели, подсказке и метке доступности индикатора после возврата обозначения раскладки.
- При `isRecoveryAvailable == true` сообщение восстановления имеет приоритет независимо от `lastFailure`: предлагает проверить поле, при необходимости использовать `Copy Original Text` и сообщает о паузе до очистки восстановления. Подтверждённая очистка синхронизируется через `showRecovery(false)`; сообщение исчезает, но ещё активный краткий сигнал может дожить до дедлайна.

Без восстановления `outcomeMessage` различает неподдерживаемое поле, ненадёжное чтение (`noTextAccess` / `invalidSnapshot`), смену контекста, неподтверждённое выделение, недоступную подготовку ввода и отмену до передачи. Эти отказы объясняют, что текст не отправлен; `unsupportedField` дополнительно сообщает, что восстанавливать нечего. `restoredAfterFailure` сообщает о восстановленном исходном тексте без предложения ручного восстановления. Для остальных значений без `isRecoveryAvailable` возвращается `nil`; одни `needsRecovery` / `aborted(.recoveryPending)` не включают сообщение или действия восстановления без синхронизации этого признака.

Передача сообщения и владение размером панели описаны в [контрактах интерфейса](./contracts/internal-interfaces.md#связь-с-интерфейсом).

## Жизненный цикл

Ниже описание управления, **не дополнительный enum состояний**:

```text
свободен -> захват / выбор / подготовка / подтверждение выделения
  отказ до передачи -> aborted или layoutOnly -> свободен
  отмена queued -> aborted -> свободен
  handedOff -> подтверждение полного значения и курсора
    подтверждено, включая свежее позднее чтение -> replaced -> свободен
    полный преобразованный текст, неверный курсор -> одна адресная попытка
      исходное значение и курсор подтверждены -> restoredAfterFailure -> свободен
      не подтверждены -> needsRecovery
    результат частичен / отсутствует / конфликтует -> needsRecovery
needsRecovery -> Copy Original Text -> блокировка остаётся
needsRecovery -> подтверждённый Clear Recovery -> свободен
```

`busy` защищён блокировкой внутри координатора; `replacementRunning` предотвращает постановку второго хоткея до выполнения фоновой задачи. `originalForRecovery: String?` доступен снаружи как `recoveryOriginalText`; пока значение не `nil`, координатор возвращает `aborted(.recoveryPending)` новым попыткам. Поздний успех проверяется до завершения текущей операции; после `needsRecovery` фонового наблюдения с автоматическим снятием блокировки нет.

## Инварианты и пределы

- Источником служит только валидированный AX-снимок. Ни автоматического буфера обмена, ни внутреннего буфера набора нет.
- До отправки повторно проверяются привязка к `applicationPID`, живой свидетель `activationPID`, неизменный источник окна и его условия, то же окно, AX-элемент, полное значение, диапазон и поколение ввода; для неактивирующего получателя и источника `.application` нужен фактический `CFBoolean true` в `AXFocused`. Потеря источника не разрешает fallback. Поколение/время решения хоткея не перезахватываются в делегате: активность после решения до запуска координатора приводит к отказу до capability. Начальный захват ограничен абсолютным `triggeredAt + 0.3`, включая очередь и чтения; последующие подтверждения имеют отдельные монотонные дедлайны 300 мс. Новая операция требует готовности обоих перехватчиков и согласованного отпечатка/поколения события хоткея.
- Допуск панелей основан на общем наборе признаков, без списков приложений и приватных API определения получателя. Закрытие или смена панели может не изменить активацию; устаревший AX-фокус не исключён. Ограничение возраста, поколения и проверка поля сужают риск, но не доказывают поддержку всех overlay-полей и не создают независимого запроса текущей клавиатурной цели.
- Неподтверждённое выделение не разрешает ввод. Его возврат после отмены не отправленного события выполняется только при неизменном контексте и значении, без обещания безусловного восстановления курсора.
- Отсутствие результата после `handedOff` не доказывает неизменность поля. Нет field-atomicity, автоматического повтора или слепого отката; исходный фрагмент сохраняется для пользователя.
- Только наблюдаемый полный преобразованный текст с неверным курсором разрешает одну адресную попытку восстановления. Полностью корректный поздний результат не откатывается.
- `Copy Original Text` является единственной записью в буфер обмена, только по нажатию. `clearRecovery()` само не вводит текст и отказывает при `busy`; UI предварительно требует подтверждения предупреждения.
- Выход откладывается при работающей операции; при сохранённом исходнике требуется решение пользователя. Ни очистка, ни выход не отменяют переданное событие; завершение процесса уничтожает копию.
- Текстовые поля модели не журналируются. Приватный журнал содержит метаданные, ограничен 1 MiB; его модульные тесты не читают пользовательские логи.

Границы системных типов: [Apple Accessibility](https://developer.apple.com/documentation/applicationservices/axuielement), [CoreGraphics CGEvent](https://developer.apple.com/documentation/coregraphics/cgevent), [NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace). Единственный источник текущих результатов и количества тестов, статуса живой, визуальной и релизной проверки: [verification.md](./verification.md#текущий-статус). Свежая изолированная регрессия P2 и полная живая замена в [Spotlight](https://support.apple.com/guide/mac-help/search-with-spotlight-mchlp1008/mac) учитываются открытой T042; ни метаданные зонда, ни доставка в собственное неактивирующее поле стенда не заменяют её ручную часть. Подтверждения пользователем базовых сценариев OpenChamber и компоновки предшествуют изменениям Spotlight/P2 и не закрывают новые проверки.
