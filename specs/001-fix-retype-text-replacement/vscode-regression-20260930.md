# Разбор регрессии в редакторе

Дата: 2026-09-30. База: `5b60d065b41c5d7da09df17720e66dc55de91edd`, v0.10.0.
Среда: macOS 26.6.2, arm64, ISO; [VS Code](https://github.com/microsoft/vscode)
1.138.0, [Electron](https://github.com/electron/electron) 42.10.0.

## Статус

**Причины воспроизведены. Исправление приложения не готово.** Экспериментальная правка прошла
обычные сценарии, но провалила частичное выделение при холодном запуске и отклонена.
Исходники приложения и тесты возвращены к базе. Запущенный локальный bundle возвращён к исходному
бинарнику; SHA-256 совпадает с резервной копией:
`bd53e37e4d87a568c3960f8f3f88d9b61a648ceb5a4fc55fb9dfb5dd4ed92774`.

Проверки выполнялись в отдельном экземпляре редактора с временным `--user-data-dir`, отключёнными
расширениями и единственным собственным файлом `repro.txt`. Пользовательские настройки не менялись.
Подключение инспектора для скриншота происходило **после** нативной проверки холодного запуска,
чтобы инспектор не включил доступность и не скрыл дефект.

## Подтверждённые причины

### 1. Регрессия раннего отказа в ReTyper

`git blame` связывает проверку `(location: 0, length: 0)` в
`Sources/ReTyper/ReplacementFlow.swift:47–50` с коммитом `4164088` от 2026-09-24 (v0.9.3).
В v0.9.0 такого условия не было: поток начинался с копирования и выделения клавишами.

Редактор в обычном режиме сообщает пустую вспомогательную область ввода вместо документа:
`AXTextArea`, `(0, 0)`, длина 0, подпись содержит `not accessible`. Наличие текста на экране этому
не противоречит: редактируемый документ и вспомогательная область ввода — разные состояния.
ReTyper принимает эти данные за настоящую пустую строку и сразу завершает операцию.

`SystemReplacementHost.selection()` возвращает любой полученный диапазон, включая этот `(0, 0)`.
Поэтому существующий запрос `AXManualAccessibility`, вызываемый только для `nil`, не выполняется.

### 2. Запрос доступности требует учёта задержки и уведомления

В [исходнике установленной версии Electron](https://github.com/electron/electron/blob/v42.10.0/shell/browser/mac/electron_application.mm):

- `accessibilitySetValue` планирует `enableScreenReaderCompleteModeAfterDelay`;
- активация отложена на 2 секунды;
- `OnAccessibilitySupportChanged()` вызывается сразу, до отложенной активации;
- отложенный `enableScreenReaderCompleteMode` не повторяет это уведомление.

[Обработчик уведомления](https://github.com/electron/electron/blob/v42.10.0/shell/browser/api/electron_api_app.cc)
отправляет текущее `IsAccessibilitySupportEnabled()`. Установленный редактор передаёт это значение
рендереру через `vscode:accessibilitySupportChanged`.

Опыт на отдельном процессе: первый `AXManualAccessibility=true`, ожидание 2,5 с — поле по-прежнему
пустое. Второй запрос — через 0,3 с виден настоящий текст и режим Screen Reader Optimized.
После этого неизменённый ReTyper v0.10.0 преобразовал `ghbdtn` → `привет` (журнал 21:50:10).
Текущее ожидание ReTyper 300 мс для такого холодного запуска недостаточно.

### 3. Чтение флага не доказывает отказ

Геттер `AXManualAccessibility` сравнивает режим через точное равенство с `kAXModeComplete`.
А setter включает также `kFromPlatform` и `kScreenReader`. API приложения проверяет вхождение
флагов через `has_mode`, а не точное равенство. Поэтому геттер продолжает отдавать `0` даже когда
редактор уже доступен. Прежний вывод в обсуждении «флаг не включился» был ошибочным.

### 4. После активации положение курсора может оставаться устаревшим

В первом кандидате текст после активации уже виден, но диапазон остаётся `(0, 0)`.
Первая операция отменяется, последующие операции после нового ввода работают.
Во втором кандидате ранний отказ убран: выполняется выделение клавишами с обязательной проверкой
его длины до копирования. Это исправляет обычный ввод, **но не сохраняет произвольное исходное
выделение** при холодной активации.

Критический сценарий: `prefix ghbdtn`, вручную выделено только `ghbdtn`.
Ожидалось `prefix привет`; получено `зкуашч привет` (журнал 22:02:00).
После активации устаревший нулевой диапазон скрыл исходное выделение, и команда выделения расширила
его до начала строки. Кандидат отклонён, а не объявлен исправлением.

## Почему прежние проверки пропустили проблему

- Поддельный host в unit-тестах отдаёт согласованный диапазон сразу, не моделирует холодный редактор.
- Нативный стенд использует настоящее текстовое поле с достоверным диапазоном; он не воспроизводит
  вспомогательную область ввода редактора.
- Ручная проверка 2026-09-25 не записывала холодный запуск, исходное состояние доступности и
  произвольное выделение. Общий журнал не содержит приложения; его записи недостаточны для
  восстановления тех условий. Почему конкретно та сессия работала, по-прежнему не установлено.
- Успех подготовленного редактора не подтверждает первую замену после его запуска.

## Дополнительные проблемы сборки

Новый локальный [SwiftPM](https://github.com/swiftlang/swift-package-manager) использует другой
движок по умолчанию и каталог `.build/out/...`. Существующие `.build/<arch>/release/ReTyper`
после такой команды остались от 25 сентября. Это замечено до запуска кандидата. Для эксперимента
обе архитектуры пересобраны с `--build-system native`, проверены свежие файлы и `minos 12.0`.
`build.sh` пока использует жёсткий путь `.build/debug/ReTyper`; адаптация сборочного сценария
остаётся отдельным незавершённым вопросом, успешная команда сборки сама по себе не подтверждает
свежесть упакованного файла.

Тест упаковки на текущем инструменте падает на `lipo file -verify_arch arm64 x86_64` с
`requires exactly one input file`, хотя `lipo -archs` видит обе архитектуры. Каждая отдельная
проверка работает. `scripts/package-release.sh` и `scripts/test-package-release.sh` исправлены:
архитектуры проверяются по одной. После правки полный тест упаковки прошёл, включая отказ на
неполной архитектуре, подменённом DMG и нарушенной подписи ZIP.

## Требования к следующему исправлению

Сначала воспроизводить холодный запуск с **частичным** выделением, затем без выделения и на
настоящем начале строки. Нельзя принимать вспомогательный `(0, 0)` за достоверную позицию и нельзя
подменять неизвестное исходное выделение выделением всей строки.

Кандидат направления: подготовка доступности при активации редактора до набора и выделения,
с обработкой ещё не готового состояния. Это изменение жизненного цикла требует отдельного
согласования и проверки: один только повтор AX-запроса недостаточен.

Релиз и коммит не выполнялись. Терминальная фича 003 остаётся незавершённой.
