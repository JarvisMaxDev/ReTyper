### Ошибка уборки окон стенда — остановка владельцем

Владелец сообщил о множестве оставленных окон и показал диалог «Прервать» с процессом `cat`.
Причина по коду: после сценария драйвер отправлял ⌘W, ждал 0,2 с и открывал следующее окно,
не проверяя фактическое закрытие и не обрабатывая диалог. При исключении/focus loss уборки не было.
Это ошибка стенда; остановки из-за фокуса нельзя приписывать действиям владельца без доказательств.

По запросу остановлены дальнейшие прогоны. Через AX закрыты **четыре** оставшихся собственных
окна `retyper-terminal-*` (T5, T7, T4, T1), подтверждение «Прервать» нажималось только в них.
Последующая проверка: собственных окон и процессов `terminal-driver`/`retyper-terminal` нет.

Исправлен `Tools/ReTyperStand/TerminalDriver.swift`:
- закрытие по уникальной идентичности своего окна, включая окно в фоне;
- обработка его подтверждения «Прервать»/`Terminate`;
- ожидание исчезновения AX-окна до 5 с; при неуспехе следующий сценарий не открывается;
- `defer` убирает открытое окно также при исключении, потере фокуса и ошибке готовности;
- результат теста сохраняется до cleanup; ошибка cleanup не объявляется успешным прогоном.

После разрешения владельца продолжить cleanup проверен на одном окне: закрытие подтверждено,
окон/процессов не осталось. При следующей серии выявлены ещё два варианта: временный отказ
AX во время закрытия и диалог «Закрыть» вместо «Прервать». Драйвер теперь ограниченно ждёт
реальный список AX-окон, обрабатывает оба варианта и появление кнопок после появления sheet.
При этих отказах следующий сценарий не открывался, оставшееся своё окно было закрыто.

### Разбор дефекта VS Code, 2026-09-30

Инструмент в `$TMPDIR/opencode/retyper-003/axfocus-src/` активирует VS Code, читает системный
фокусный элемент так же, как `FocusedText` (только роль, диапазон, длины, ключевые слова подписи —
без текста), и возвращает фокус предыдущему приложению. Для вкладки редактора он нажимает ⌘1.

| Фокус | Роль | `AXSelectedTextRange` | символов / длина `AXValue` | Подпись (aria-label) содержит |
|-------|------|-----------------------|----------------------------|-------------------------------|
| панель терминала | `AXTextField` | (0, 0) | 0 / 0 | «terminal», «screen reader» |
| вкладка редактора | `AXTextArea` | (0, 0) | 0 / 0 | «not accessible», «editor», «screen reader» |

`AXManualAccessibility` у VS Code = 0. VS Code запущен 2026-09-30 21:20:25, за 24 с до первого
хоткея T002.

Механизм (проверено по коду): VS Code вне режима для экранного диктора отдаёт пустое скрытое поле с
кареткой (0, 0). `ReplacementFlow.run` считает (0, 0) «перед кареткой ничего нет» и сразу
завершается `layoutOnly`. `SystemReplacementHost.selection()` запрашивает `AXManualAccessibility`
только когда выделение неизвестно (nil), поэтому для такого поля флаг не включается никогда.

**Опыт с `AXManualAccessibility`, 2026-09-30, с согласия владельца** (`axmanual-src/`): VS Code
активирован, фокус во вкладке редактора, `AXUIElementSetAttributeValue(app, "AXManualAccessibility",
true)` → `err=0`, повторное чтение флага → 0. Снимки поля через 0,1 / 0,3 / 0,6 / 1 / 2 / 3 с: все
`AXTextArea`, (0, 0), 0 символов, подпись «not accessible». **Флаг не переводит редактор VS Code
1.138.0 в доступный режим**; вариант исправления A в исходном виде не работает.

Не проверено: почему 2026-09-25 VS Code работал. Предположение: тогда VS Code был в режиме для
экранного диктора (флаг включён раньше в той же сессии VS Code), и поле отдавало настоящую строку.

### S4 — защищённый ввод на запросах пароля (T005)

| Случай | `kCGSSessionSecureInputPID` | `IsSecureEventInputEnabled()` | tap увидел нажатий из 3 | Итог |
