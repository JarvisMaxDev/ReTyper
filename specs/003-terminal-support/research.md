# Research: Преобразование текста в терминалах

**Дата**: 2026-09-29 | **Спецификация**: [spec.md](./spec.md) | **План**: [plan.md](./plan.md)

Замеры сделаны 2026-09-29 на машине владельца: macOS 26.6.2 arm64, клавиатура ISO
(`LMGetKbdType()` = 62), текущая раскладка Polish Pro. Черновые скрипты замеров лежали в
`/tmp/retyper-003/` и в репозиторий не входят.

Статусы: **проверено** — есть замер или чтение кода/заголовка SDK; **не проверено** — решение
принято по документации или рассуждению, проверяется спайком S1–S4 до основной реализации
([quickstart §1](./quickstart.md#1-спайки-до-основной-реализации)).

## R1. Как узнать, какой символ напечатан

**Decision**: в callback CGEventTap для каждого `keyDown` в поддерживаемом терминале брать код
клавиши и Shift, читать текущую раскладку и получать символ из `KeyLayout` этой раскладки (тот же
источник, что у преобразования, фича 002). `KeyLayout` для раскладки строится один раз и
кешируется по паре «ID раскладки, тип клавиатуры».

**Rationale**:
- Принцип II: символы берутся из данных раскладок macOS, как и при преобразовании. Запомненный
  текст и преобразование используют одни данные, поэтому обратное преобразование даёт исходные
  клавиши.
- `TISCopyCurrentKeyboardInputSource` + ID стоит около 0,3 мкс на вызов (2000 вызовов, два прогона,
  **проверено**). В горячем пути это допустимо.
- Построение `KeyLayout` для одной раскладки — около 1 мс (фича 002, R3: 1,3 мс на пару). Происходит
  один раз на раскладку за запуск; кеш из 2–3 записей.

**Alternatives considered**:
- `CGEventKeyboardGetUnicodeString` у перехваченного события. Заголовок SDK
  (`CGEvent.h`) говорит, что строка по умолчанию строится «по keyboard ID в источнике события»; учёт
  текущей раскладки не гарантирован. Отвергнуто: нет гарантии совпадения с тем, что напечатал
  терминал.
- Хранить коды клавиш и переводить в символы только при хоткее. Отвергнуто: мёртвые клавиши (R3) и
  смену раскладки посреди набора пришлось бы разбирать задним числом; запомненная строка символов
  проще.

**Не проверено**: успевает ли `TISCopyCurrentKeyboardInputSource` вернуть новую раскладку, если
пользователь начал печатать сразу после её переключения. Спайк S3.

## R2. Какие нажатия пополняют фрагмент, какие сбрасывают

**Decision** (FR-002, FR-003):

| Нажатие | Действие |
|---------|----------|
| Клавиша основного блока без модификаторов или с одним Shift, есть в `KeyLayout` текущей раскладки и не мёртвая | добавить символ |
| Пробел (код 49) без модификаторов или с Shift | добавить пробел |
| Backspace (код 51) без модификаторов | удалить последний символ; если фрагмент пуст — ничего |
| Return, Enter, Tab, Escape, стрелки, Home, End, Page Up/Down, Forward Delete, F-клавиши, цифровой блок | сброс |
| Любое нажатие с ⌘, ⌃ или ⌥ (включая ⌥Backspace, ⌃W, ⌘V, ⌘1) | сброс |
| Нажатие при включённом Caps Lock | сброс |
| Мёртвая клавиша (R3) или клавиша, которой нет в `KeyLayout` | сброс |
| Нажатие мыши (левая, правая, другая кнопка) в любом месте | сброс |
| Активация другого приложения, в том числе возврат в терминал | сброс |
| Смена рабочего стола (`NSWorkspace.activeSpaceDidChangeNotification`) | сброс |
| Смена фокусного окна того же терминала без клавиатуры и мыши (жест, Mission Control) | ловится сверкой окна перед заменой ([R6](#r6-прерывание-во-время-замены-fr-009)) |
| Автоповтор | каждое событие обрабатывается как отдельное нажатие |
| Синтетические нажатия ReTyper (маркер `syntheticEventMarker`) | игнорируются, как сейчас |
| Нажатие Fn / 🌐 (`flagsChanged`, коды 63 и 179) | сброс: диктовка и панель эмодзи вставляют текст без `keyDown` |
| Остальные изменения модификаторов (`flagsChanged`), в том числе сам хоткей | не меняет фрагмент |

После сброса фрагмент пуст; хоткей даёт «только смену раскладки», пока не набран новый текст.

**Rationale**: всё, что может изменить строку не так, как мы видим по нажатиям (перемещение
курсора, автодополнение, история, вставка, редактирование с модификаторами), сбрасывает фрагмент.
Список консервативный: пропущенное исправление безопаснее испорченной команды (User Story 2).

Caps Lock сбрасывает, потому что `KeyLayout` описывает только состояния без Shift и с Shift, а
Caps Lock влияет на буквы и не влияет на цифры. Если в системе Caps Lock назначен на переключение
раскладки, флаг Caps Lock обычно не остаётся включённым; это **не проверено** и в сценарии
владельца не встречается.

Вкладки и окна одного терминала: переключение щелчком — сброс по мыши; переключение ⌘-сочетанием —
сброс по модификатору. Отдельное отслеживание вкладок не нужно.

**Alternatives considered**: сохранять фрагмент после стрелок и учитывать позицию курсора.
Отвергнуто: оболочка может по-разному трактовать стрелки (история, меню дополнения), и узнать это
снаружи нельзя.

## R3. Мёртвые клавиши

**Decision**: `KeyLayout.system` дополнительно отмечает клавиши, которые без модификаторов или с
Shift работают как мёртвые (после `UCKeyTranslate` без `kUCKeyTranslateNoDeadKeysMask` остаётся
ненулевой `deadKeyState`). Нажатие такой клавиши сбрасывает фрагмент.

**Rationale** (**проверено** скриптом на ISO):

| Раскладка | Мёртвые клавиши без ⌥ (код, S = с Shift) |
|-----------|-------------------------------------------|
| Polish Pro, Russian – PC, Russian, U.S., ABC, Ukrainian | нет |
| U.S. International – PC | 22S, 39, 39S, 50, 50S |
| German | 10, 24, 24S |
| French | 33, 33S, 42 |

Сейчас `KeyLayout` для таких клавиш хранит их собственный символ (`^`, `´`). Терминал же после
мёртвой клавиши ждёт следующую и печатает составной символ либо два символа. Запоминать это
надёжно нельзя, поэтому сброс. В раскладках владельца мёртвых клавиш нет, основной сценарий не
затронут.

## R4. Как ввести исправленный текст

**Decision**: удалить фрагмент нажатиями Backspace (код 51), по одному на символ, и ввести
преобразованный текст синтетическими `keyDown`/`keyUp`, у которых строка задана через
`CGEventKeyboardSetUnicodeString`, по одному символу на событие. Все события помечаются
`syntheticEventMarker`. Буфер обмена не используется.

**Rationale**:
- Число символов удаления известно точно: каждый запомненный символ дало одно нажатие, и это одна
  кодовая точка (R5).
- Ввод строкой не зависит от того, переключилась ли уже раскладка в терминале. Альтернатива «сменить
  раскладку и повторить те же коды клавиш» зависит от гонки между переключением раскладки и
  доставкой событий.
- Буфер обмена не трогается: FR-010 выполняется без снимка и восстановления, нет запроса macOS 15.4+
  о чтении буфера, менеджеры буфера ничего не видят.

**Не проверено**: заголовок `CGEvent.h` предупреждает, что «application frameworks may ignore the
Unicode string in a keyboard event and do their own translation based on the virtual keycode».
Принимает ли Терминал строку из события — спайк S1. Если нет — запасной путь: вставка через ⌘V из
буфера обмена по правилам фичи 001 (снимок, маркеры nspasteboard.org, восстановление через 0,5 с);
решение о переходе фиксируется в `verification.md` до реализации.

**Alternatives considered**:
- Вставка через буфер обмена сразу. Отвергнуто как основной путь: лишнее касание буфера, запрос
  разрешения, подсветка bracketed paste в zsh. Оставлено запасным.
- ⌃W или ⌃U для удаления. Отвергнуто: удаляют по словам или всю строку, а не ровно фрагмент.

## R5. Сколько символов стирает Backspace в оболочке

**Decision**: одно нажатие Backspace = один запомненный символ.

**Rationale**: каждый запомненный символ получен из `KeyLayout`, где символ клавиши — ровно одна
кодовая точка без управляющих (`printedCharacter` в `KeyLayout.swift` отбрасывает остальное).
Построчные редакторы оболочек ([zsh ZLE](https://zsh.sourceforge.io/Doc/Release/Zsh-Line-Editor.html),
[GNU Readline](https://tiswww.case.edu/php/chet/readline/rltop.html) в bash) в UTF-8-локали удаляют
по Backspace одну кодовую точку. **Не проверено** на машине: сценарии quickstart со строкой из
кириллицы подтверждают это для zsh в Терминале (спайк S1).

## R6. Прерывание во время замены (FR-009)

**Decision**: перед началом замены проверить, что активно то же приложение, то же фокусное окно
(`AXFocusedWindow` приложения, сравнение через `CFEqual`, таймаут AX 0,25 с, как в `FocusedText`) и
что фрагмент не менялся после хоткея (у фрагмента есть счётчик изменений: любой символ, Backspace
или сброс, в том числе щелчок мыши, его увеличивает). Окно фрагмента читается не в callback tap, а
сразу после него через `DispatchQueue.main.async`, когда фрагмент из пустого становится непустым.
Неизвестное окно с любой стороны — замены нет. Так ловится смена окна жестом или через Mission
Control, при которой нет ни нажатия клавиши, ни щелчка. Если проверка прошла, послать удаление и ввод одной серией до конца
(вариант «дописать»). После серии снова сравнить счётчик нажатий; если пользователь печатал во время
серии, записать в журнал `interleaved input` (без текста) и сбросить фрагмент.

Нажатия отправляются с удержанием 1 мс, как сейчас `shrinkSelectionFromStart`. Оценка: примерно
2 мс на символ удаления и 2 мс на символ ввода, то есть около 40 мс для 10 символов и около 400 мс
для 100 (SC-004 требует < 1 с). Замер — спайк S2.

**Rationale**: остановка посреди серии оставила бы строку частично стёртой, что хуже любого другого
исхода. Сама серия короткая.

**Остаточный риск** (записать в README): tap работает в режиме `listenOnly` и не может задержать
нажатия пользователя. Если пользователь нажмёт клавишу в эти 40–400 мс, его символ попадёт между
синтетическими событиями: он может быть стёрт следующим Backspace вместо символа фрагмента, и в
строке останется один лишний исходный символ. ReTyper обнаружит это и запишет в журнал, но не
исправит.

Полное исключение требует перевести tap в активный режим и задерживать ввод пользователя на время
серии. Это меняет свойство «монитор никогда не задерживает ввод» и усложняет горячий путь, поэтому
в эту фичу не входит. Предлагаемая поправка конституции оговаривает этот риск явно (plan.md).

## R7. Защищённый ввод и пароли (FR-007)

**Decision**: при хоткее проверять `IsSecureEventInputEnabled()`; если защищённый ввод включён
любым процессом — сброс и только смена раскладки. Пока защищённый ввод включён, macOS не передаёт
event tap нажатия клавиш, поэтому пополнять фрагмент нечем.

**Rationale**: заголовок `CarbonEventsCore.h` (**проверено**): функция возвращает true, если
защищённый ввод включён в любом процессе. Для «Secure Keyboard Entry» Терминала этого достаточно.

**Проверено спайком S4, 2026-09-30** ([verification.md](./verification.md#s4--защищённый-ввод-на-запросах-пароля-t005)):
на запросе `sudo` Терминал включает защищённый ввод, и tap не получает нажатий; на `read -s` в zsh
защищённый ввод не включается, и tap получает все нажатия. Владелец выбрал вариант A: скрытый ввод
без защищённого ввода обрабатывается как обычный — символы только в памяти, до ближайшего Enter
(FR-007 уточнён). Отличать такие запросы по режиму tty вкладки не пытаемся: без AppleScript
(новое разрешение Automation, запрещено FR-016) надёжного способа узнать tty вкладки нет.

## R8. Какие терминалы получают замену (FR-013, FR-014)

**Decision**: список терминалов делится на два:
- `typingTerminalBundleIDs` — терминалы с заменой. Сначала только `com.apple.Terminal`.
- Остальные (iTerm2, Warp, Ghostty, kitty, Alacritty, WezTerm, Hyper) — только смена раскладки,
  как сейчас. Терминал переходит в первый список только после прохождения сценариев quickstart в
  нём.

Фрагмент пополняется, только пока активно приложение из первого списка. VS Code, WebStorm и прочие
приложения в эти списки не входят, их путь не меняется.

**Rationale**: на машине установлен только Терминал (**проверено** через `mdfind` 2026-09-25).
Kitty, Ghostty и Alacritty обрабатывают клавиши сами и могут не принять строку из события (R4),
поэтому без проверки их включать нельзя.

## R9. Повторный хоткей (FR-011)

**Decision**: после успешной замены фрагмент становится «часть до заменённого + преобразованный
текст». Повторный хоткей без нового ввода преобразует его обратно по обычным правилам фичи 002.
Отдельная сущность «последняя замена» не нужна.

**Rationale**: для взаимно-однозначных пар раскладок обратимость уже гарантирована и покрыта
тестами фичи 002 (FR-009 той фичи). Для фрагмента только из общих символов направление берётся по
текущей раскладке, которая после замены уже переключена, поэтому откат тоже работает.

## R10. Предел длины и время жизни (FR-005, FR-006)

**Decision**: предел — 256 символов. Когда фрагмент превышает предел, текст очищается
(конституция 7.0.0, принцип III: превышение предела — сброс), и до ближайшего сбрасывающего
действия новые символы не запоминаются: без начала строки их замена преобразовала бы слово
наполовину. Хоткей в это время даёт только смену раскладки. Фрагмент очищается также при
сбросе (R2), при защищённом вводе (R7) и при выходе из ReTyper. Если хоткей закончился только
сменой раскладки (например, направление не определено), фрагмент не меняется: символы в строке
остались прежними. Хранится только в памяти `KeyboardMonitor`; в журнал идут длина и исход.

**Rationale**: 256 символов с запасом покрывают обычную команду; при 2 мс на символ серия для
256 символов укладывается примерно в 1 с. Переполнение не обрезает фрагмент до последних 256
символов, потому что обрезанный фрагмент не соответствует строке; держать его в памяти незачем
(принцип I).

## R11. Автоматическая сквозная проверка

**Decision**: расширить `Tools/ReTyperStand` терминальными сценариями. Driver открывает окно
Терминала файлом `.command` (через `open`, без Automation), в окне запускается
`zsh -f -c 'vared -c line; print -rn -- $line > <out>'`. Driver печатает текст обычными
нажатиями по кодам клавиш (для ReTyper это ввод пользователя), нажимает двойной ⌥, затем Return и
сравнивает файл с ожидаемой строкой. Так проверяется то, что получила оболочка (SC-001), без
чтения экрана.

**Rationale**: `vared` использует тот же редактор ZLE, что и интерактивная строка zsh.
Нажатия посылаются только пока активен Терминал, как стенд делает для своего окна.

**Не проверено**: закрывается ли окно после выхода скрипта при текущих настройках профиля
Терминала; при необходимости driver закрывает его сам через Accessibility.
