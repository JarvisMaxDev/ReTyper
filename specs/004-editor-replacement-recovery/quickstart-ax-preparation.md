# Архив проверки: отклонённая AX-подготовка

Дата: 2026-09-30. **Это инструкция будущей проверки, а не выполненный прогон.**
Записывать результат, ревизию, версии приложений и hash бинарника в `verification.md` этой фичи.

## 1. Предусловия

- Тестовый документ без пользовательских данных; отдельный профиль редактора.
- Исходный ReTyper и проверяемый кандидат запускаются по одному, не одновременно.
- Текущие разрешения Accessibility/Input Monitoring; Polish и Russian – PC.
- Не включать постоянную настройку screen-reader; инспектор подключать только после проверки
  холодного запуска, иначе он может скрыть дефект.
- Вспомогательные процессы и окна принадлежат проверке; пользовательский редактор не перезапускается.

## 2. Проверки реализуемости — до основной реализации

### P0-01: готовность без изменения выделения (обязательный гейт)

Проверить прототип фоновой подготовки до написания production-пути замены:

1. Редактор стартует после ReTyper. До готовности выделить `ghbdtn` в
   `prefix ghbdtn suffix`, в обоих направлениях. Подготовка не меняет выделение.
2. Редактор уже содержит это выделение; затем запускается ReTyper. Те же требования.
3. Для обоих случаев сравнить реальное выделение тестового документа с AX-наблюдением:
   до запросов, после первого, после задержки, после второго, после завершения подготовки.
   Эталон — сохранённая собственная строка и визуально подтверждённые границы выделения на
   снимке окна, а не AXSelectedTextRange и не факт отправки клавиш. В кадре должны быть
   видны префикс, выделенное слово и суффикс; если границы неразличимы, результат INCONCLUSIVE,
   не PASS. Снимок не должен активировать приложение или открывать инспектор. Не копировать
   выделение для получения эталона. После замены сверять собственный сохранённый документ.
   Если нативный захват недоступен, допустим pixel-only Page.captureScreenshot без включения
   Accessibility/DOM/Runtime; отдельными чтениями до/после подтвердить отсутствие прогрева AX.
4. Не исправлять состояние стрелками, повторным выделением, сменой фокуса или режимов вручную.
5. Хоткей во время подготовки: текст и выделение прежние. Новый хоткей после готовности:
   строго `prefix привет suffix`, без требования набрать дополнительный символ.
6. Затем проверить строку без выделения, настоящее начало строки и пустой документ.

PASS: документирован достаточный критерий готовности, а все перечисленные случаи проходят
10/10. FAIL: отличить настоящее выделение от устаревшего невозможно, для успеха требуется
вмешательство в документ/каретку либо операция меняет префикс/суффикс. При FAIL — остановиться
и пересмотреть архитектуру, не ослаблять критерий и не скрывать отказ под PASS.

### P0-02: контекст операции

Во время каждого этапа (prepare/select/copy/paste/cleanup) сменить окно, поле, вкладку одного
процесса, уйти в другое приложение и вернуться. Документировать, какие события и identity
элементов это обнаруживают. Повторно используемый элемент/окно не разрешает вставку старого
результата. Проверить завершение и перезапуск процесса с поздним ответом старой попытки.

PASS: все смены контекста останавливают дальнейшие команды; ни одной поздней вставки или стрелки
в другом поле. Необнаружимая смена — блокер, а не незаявленная поддержка.

### P0-03: границы редактора

Отличить обычный редактор, поиск, встроенную терминальную панель и защищённое поле без
локализованного заголовка как единственного признака. При системном secure input не посылать
копирование/вставку; сам хоткей может не поступить. Встроенный терминал остаётся layout-only.

PASS: подтверждены признаки пригодного редактора и отказ во всех запрещённых контекстах.
Неоднозначность оставляет поле unverified. Если это делает обычный редактор постоянно
неработающим, это FAIL восстановления, а не успешное защитное поведение.

## 3. Автотесты после гейтов

Из корня репозитория:

```bash
swift test --build-system native
```

Ожидается полный прежний набор плюс тесты жизненного цикла, двух отложенных запросов,
ошибок/таймаутов, повторного PID, старых callback, раздельной модели действительного выделения
и AX-ответа, отмены перед каждым эффектом. При чистой каретке не должно быть copy.
Собственное выделение снимается только в исходном контексте. Жест хоткея не зависит от мыши.

## 4. Проверка свежести release-кандидата

Команды временно используют проверенный `native` build engine. Если он недоступен, сначала
адаптировать сценарий и проверить путь/минимальную систему; не подставлять старые файлы.

```bash
swift build --build-system native -c release --arch arm64
swift build --build-system native -c release --arch x86_64
swift build --build-system native -c release --arch arm64 --show-bin-path
swift build --build-system native -c release --arch x86_64 --show-bin-path
lipo -create .build/arm64-apple-macosx/release/ReTyper \
  .build/x86_64-apple-macosx/release/ReTyper -output ReTyper-universal
xcrun vtool -show-build ReTyper-universal
lipo ReTyper-universal -verify_arch arm64
lipo ReTyper-universal -verify_arch x86_64
bash scripts/test-package-release.sh
```

Ожидаются обе архитектуры и `minos 12.0`. Перед копированием в bundle завершить только
известный процесс ReTyper, сохранить предыдущий бинарник для отката. Затем подписать и проверить
bundle (`codesign --force --sign - ReTyper.app`, `codesign --verify --deep --strict ReTyper.app`),
запустить его и сравнить hash установленного бинарника с собранным. Это отдельное проверяемое
действие; исторический путь в `.build/` не доказывает свежесть.

## 5. Полная приёмка на свежем кандидате

```bash
Tools/ReTyperStand/run.sh
```

- Все 11 сценариев должны пройти.
- Повторить P0-01–03 против полного приложения, не только прототипа.
- US1.1–3: по 10 повторов в холодном и подготовленном редакторе, частичные выделения обоих
  направлений, последнее слово, настоящий пустой ввод. Сверять сохранённый собственный документ,
  не только исход `replaced` в журнале.
- Замерять от завершения жеста до наблюдаемого изменения документа; запись журнала не равна
  завершению изменения в редакторе. SC-003: максимум ≤1 с после подготовки для 100 символов.
- Режим подготовки имеет свой бюджет ≤4 с и отдельный результат; не смешивать его с обычной заменой.
- Проверить сохранность clipboard: текст и нетекстовый тип, а также чужое копирование во время операции.
- Проверить notNeeded на обычном нативном поле: специального setter и задержки нет, замена работает.
- Раздельно проверить сообщения preparing/failed/unverified/unsupported, их исчезновение через
  3 с, отсутствие смены фокуса и отсутствие повторных AX-запросов на каждый хоткей после failed.
- Повторить обычные сценарии в ещё одном реальном приложении с текстовым полем.
- Зафиксировать свежие скриншоты холодного частичного выделения до и результата после операции.
- Проверить весь журнал на известные уникальные строки стенда. Отсутствие текста проверяется
  отдельно от успешности замены.
- WebStorm: «не проверено», пока нет лицензии; не засчитывать за него другой редактор.

При любом повреждении текста — откат кандидата и блокировка выпуска. Коммит/пуш — только
по явному запросу; после разрешённого пуша обязателен успешный CI публикуемой ревизии.
