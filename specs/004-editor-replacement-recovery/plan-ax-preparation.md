## Summary

Восстановить замену текста в обычном редакторе с сохранением пользовательского выделения.
Исправляется интеграция с редактором, а не правила преобразования раскладок.

Установленные причины: ранний отказ по фиктивному `(0,0)`; обход подготовки только при `nil`;
задержанная активация доступности и преждевременное уведомление в Electron; устаревшее положение
каретки после включения режима. Подробности и отклонённый кандидат —
[в разборе](../001-fix-retype-text-replacement/vscode-regression-20260930.md).

Кандидат решения:
1. Готовить приложение в фоне при его запуске/активации, максимум двумя запросами на попытку.
2. Отдельно определять пригодность конкретного поля и достоверность исходного выделения.
3. Привязывать операцию к процессу, окну, полю и ревизии контекста; отменять при изменении.
4. Использовать существующие выделение/copy/convert/paste только после выполнения условий.
5. Во время подготовки сообщать состояние без перехвата фокуса; старые хоткеи не воспроизводить.

Нет возврата к слепому copy, удаления перед paste, изменения пользовательских preferences или
использования набранного буфера из терминальной фичи.

## Technical Context

**Language/Version**: [Swift](https://www.swift.org/) 5.9 language mode, существующий
[SwiftPM](https://github.com/swiftlang/swift-package-manager) executable/test target.

**Primary Dependencies**: существующие Cocoa, Carbon, CoreGraphics;
[NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace) для жизненного цикла,
[Accessibility](https://developer.apple.com/documentation/applicationservices/axuielement) для
контекста поля. Новых runtime-зависимостей нет.

**Storage**: память процесса для состояния подготовки и снимка контекста; существующий
clipboard snapshot только во время явной замены. Новых файлов/preferences с вводом нет.

**Testing**: [XCTest](https://developer.apple.com/documentation/xctest), существующий нативный
стенд и новый воспроизводимый cold-editor сценарий на отдельном профиле.

**Target Platform**: macOS 12.0+, arm64 и x86_64. Первая фактическая среда — macOS 26.6.2,
VS Code 1.138.0 / Electron 42.10.0. Проверка других сочетаний учитывается отдельно.

**Project Type**: нативное menu-bar desktop-приложение.

**Performance Goals**: подготовка одной попытки ≤4 с, один повтор после 2,5 с, AX-вызов ≤250 мс;
замена ≤100 символов после готовности ≤1 с по наблюдаемому документу.

**Constraints**: неблокирующая подготовка; отсутствие эффектов при неопределённом выделении;
runtime-режим доступности может включиться, пользовательские settings не переписываются;
конвертер, хоткей и разрешения совместимы с текущими.

**Scale/Scope**: один текущий foreground-получатель; записи только для наблюдавшихся процессов,
очистка при завершении; один незавершённый запрос замены, без очереди старых хоткеев.

**Нерешённые технические вопросы**: доказательство достоверности выделения (P0-01), обнаружение
смены получателя/вкладки (P0-02), надёжное отличие терминальной панели (P0-03). Они явно блокируют
production-реализацию; отсутствие текстового маркера NEEDS CLARIFICATION не означает их решения.

## Phase 0: порядок снятия блокеров

1. P0-01: воспроизвести частичное выделение до завершения фоновой подготовки; оба порядка
   запуска приложений, оба направления выделения. Получить достаточный критерий актуальности
   либо отклонить гипотезу. Не начинать production-путь до результата.
2. P0-02: подтвердить идентификацию получателя и отмену, включая смену поля/вкладки внутри PID

3. P0-03: подтвердить границы editor/terminal/secure и отсутствие редакторных команд в терминале.
4. Записать результаты в новый `verification.md`; обновить research и этот гейт. По запросу
   владельца создан `tasks.md` с исполнимыми исследовательскими задачами и условной декомпозицией.
   Только при PASS всех трёх финализировать интерфейсы и разрешить основные задачи через T008.

Подробная процедура — [архив quickstart §2](quickstart-ax-preparation.md#2-проверки-реализуемости--до-основной-реализации).
Если P0-01 провален, не развивать второй и третий пункты ради формального завершения; сначала
пересмотреть архитектуру с владельцем.

## Phase 1: условный дизайн

**Application preparation**: небольшой отдельный `ElectronAccessibility` хранит identity запуска,
token попытки и состояния. Подключается к событиям запуска/активации/завершения из AppDelegate,
первично обрабатывает активное приложение при старте ReTyper. Проверка наличия атрибута и запросы
в фоне. Failed запрос не кешируется как готовность. Поздние callback старого процесса игнорируются.
Отсутствие атрибута даёт `notNeeded`, не запрет работы: обычное нативное поле проверяется без
протокола подготовки. Ошибка чтения атрибутов не считается их отсутствием.

**Selection + context**: `SystemReplacementHost` получает наблюдение и связанную identity
получателя. `ReplacementFlow` использует его достоверность, а не предполагает, что любой диапазон
валиден. Терминальное/защищённое/неподтверждённое поле исключается до команд.
Конкретный предикат достоверности фиксируется только результатом P0-01.

**Cancellation**: события смены контекста увеличивают revision. Перед командами сверяются
identity, revision и secure input. Добавление событий мыши при необходимости не меняет жест
хоткея; только инвалидирует операцию. Собственное выделение снимается лишь в исходном контексте.

**Feedback**: раздельные preparing/failed/unverified/unsupported согласно FeedbackState модели,
только по хоткею, на 3 с или до смены контекста. Без активации окна и нового системного разрешения.
Это сообщение об отказе/подготовке, не подтверждение успешной замены.

Модель: [data-model-ax-preparation.md](data-model-ax-preparation.md). Контракт: [архив](contracts/editor-hotkey-ax-preparation.md).

## Complexity Tracking
